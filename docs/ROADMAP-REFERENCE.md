# 로드맵 레퍼런스 (범용 템플릿)

새 프로젝트의 `docs/ROADMAP.md` 를 쓸 때 복사해서 채우는 기준 문서입니다.
FastAPI 백엔드, 프론트엔드, DB, AI/LLM, 인프라 등 작업 종류와 상관없이 같은 형식을 씁니다.

**이 파일을 쓰는 법**

1. [A. 로드맵 골격](#a-로드맵-골격-복사해서-채우기)을 통째로 복사해 `docs/ROADMAP.md` 로 만든다.
2. `<꺾쇠>` 자리를 프로젝트 내용으로 바꾼다.
3. Task 를 쓸 때는 [B. Task 템플릿](#b-task-템플릿)을 쓰고, 산출물과 완료 기준은 [C. 작업 유형별 체크리스트](#c-작업-유형별-체크리스트)에서 해당 유형을 골라 붙인다.
4. 쓰는 동안 [D. 작성 원칙](#d-작성-원칙)을 지킨다.

## A. 로드맵 골격 (복사해서 채우기)

````markdown
# <프로젝트명> 개발 로드맵

<이 프로젝트가 누구의 어떤 문제를 푸는지 한 문장>

**📅 최종 업데이트**: <YYYY-MM-DD> (<이번에 바뀐 것 한 줄>)
**📊 진행 상황**: <현재 단계 한 줄> (<완료 수>/<전체 수> Tasks 완료, <퍼센트>%)

---

## 개요

<프로젝트명>은 <대상 사용자>를 위한 <제품 성격>으로 다음 기능을 제공합니다:

- **<기능 묶음 1>** — <한 줄 설명> (`F001`, `F002`)
- **<기능 묶음 2>** — <한 줄 설명> (`F003`)

**근거 문서**

| 문서                    | 역할                                         |
| ----------------------- | -------------------------------------------- |
| `docs/PRD.md`           | 기능 명세 `F001`–`F0xx`, 데이터 모델         |
| `<계획서 경로>`         | 구현 순서, 권한 설계, 검증 방법              |
| `CLAUDE.md`             | 프로젝트 컨벤션 (스택, 폴더 구조, 금지 사항) |
| `<API 명세 / 설계 문서>` | <있으면 적는다>                              |

---

## 표기 규칙

- `- [ ]` 미완료 / `- [x]` 완료
- Task 제목 뒤 `- 우선순위` 는 즉시 착수할 작업, `✅ - 완료` 는 끝난 작업
- Phase 제목 뒤 `✅` 는 그 Phase 의 모든 Task 가 끝났음을 뜻함
- 각 Task 는 **관련 기능 ID(`F0xx`)**, **산출물**, **완료 기준**을 갖는다
- 완료 기준은 "눈으로 확인하는 동작"과 "거부되어야 하는 동작(부정 테스트)"을 함께 적는다

## Phase 요약표

| Phase       | 제목              | 관련 기능     | Tasks | 완료 | 상태    |
| ----------- | ----------------- | ------------- | ----- | ---- | ------- |
| **Phase 0** | 기반 · 준비       | —             | <n>   | <n>  | <상태>  |
| **Phase 1** | <핵심 도메인 1>   | `F001` `F002` | <n>   | <n>  | <상태>  |
| **Phase 2** | <핵심 도메인 2>   | `F003`        | <n>   | <n>  | <상태>  |
| **Phase N** | 마무리 · 검증     | 전체          | <n>   | <n>  | <상태>  |
| **Phase X** | 2차 로드맵 (MVP 밖) | —           | <n>   | 0    | 대기    |
| **합계**    |                   |               | <n>   | <n>  | <퍼센트> |

상태 값: `대기` / `진행 중` / `완료 ✅` / `계획 확정 · 착수 전` / `보류`

### 단계 의존성

```
Phase 0 (기반)
    ↓
Task 00A  ← 여기까지 순서 고정 (이유: <외래키 / 인증 / 공통 모듈 의존>)
    ↓
 ┌──┴──┬────────┐
00B   00C     00D     ← 서로 독립, 병렬 가능
 └──┬──┘
   00E                ← 00B + 00C 가 모두 있어야 만들 수 있음
```

## 개발 워크플로우

1. **작업 계획** — 코드베이스 현재 상태를 파악하고, 새 작업을 로드맵에 추가한다
2. **작업 생성** — `/tasks/XXX-description.md` 에 명세, 관련 파일, 수락 기준, 구현 단계를 적는다.
   데이터·비즈니스 로직 작업은 "테스트 체크리스트" 섹션이 필수
3. **작업 구현** — 구현 → 검증 명령 통과 → 한 단계 끝날 때마다 멈추고 확인받는다
   - 검증 명령: `<프로젝트의 통합 검증 명령>` (예: `npm run validate`, `uv run ruff check . && uv run pytest`)
   - 스키마를 바꿨으면: `<파생물 재생성 명령>` (타입, 클라이언트 SDK, OpenAPI 스키마 등)
4. **로드맵 업데이트** — 완료한 항목을 `- [x]` 로 바꾸고, 요약표 숫자와 최종 업데이트 줄을 고친다
````

## C. 작업 유형별 체크리스트

Task 의 산출물과 완료 기준을 쓸 때, 해당하는 유형에서 필요한 줄만 골라 씁니다. 한 Task 가 여러 유형에 걸치면(수직 슬라이스) 여러 묶음에서 가져옵니다.

### C-1. 백엔드 API (FastAPI 기준)

**산출물에 적을 것**

- `app/api/<도메인>/router.py` — 엔드포인트 목록 (메서드 · 경로 · 요청/응답 모델)
- `app/schemas/<도메인>.py` — Pydantic 요청·응답 스키마 (입력용과 출력용 분리)
- `app/services/<도메인>.py` — 비즈니스 로직 (라우터는 얇게)
- `app/repositories/<도메인>.py` 또는 `app/models/<도메인>.py` — 데이터 접근
- `app/api/deps.py` — 인증·권한·DB 세션 의존성
- `tests/api/test_<도메인>.py` — 엔드포인트 테스트

**완료 기준 후보**

- [ ] 정상 요청 → 기대한 상태 코드와 응답 본문 (`200` / `201` / `204`)
- [ ] 스키마 위반 입력 → `422` 와 필드별 오류
- [ ] **인증 없이 호출 → `401`**
- [ ] **권한 없는 사용자가 호출 → `403`, 남의 리소스 ID → `404`** (존재 여부를 흘리지 않음)
- [ ] 중복·충돌 → `409` 와 사람이 읽을 수 있는 메시지
- [ ] 같은 요청을 두 번 보내도 결과가 같음 (멱등이어야 하는 엔드포인트)
- [ ] 목록 API 에 페이지네이션·정렬·필터가 있고 상한이 걸려 있음
- [ ] `/docs` (OpenAPI) 에 요청·응답 예시와 오류 응답이 드러남
- [ ] 외부 호출(HTTP, LLM, DB)은 `async` 이고 타임아웃이 있음
- [ ] `ruff check` · 타입 체크(`mypy` 또는 `pyright`) · `pytest` 통과

### C-2. DB · 마이그레이션

**산출물에 적을 것**

- `<마이그레이션 경로>/<타임스탬프>_<설명>` — 테이블, 컬럼, 제약(CHECK · UNIQUE · FK), 인덱스
- 권한 정책 (RLS 정책 또는 애플리케이션 계층 권한 검사 위치)
- 트리거·함수·뷰가 있으면 이름과 역할
- 시드·픽스처 데이터

**완료 기준 후보**

- [ ] 마이그레이션 적용 성공, **되돌리기(downgrade)도 성공** (예: `alembic upgrade head` → `alembic downgrade -1` → `upgrade head`)
- [ ] 제약 위반 행을 넣으면 DB 가 거부 (애플리케이션 검증과 별개로)
- [ ] **다른 사용자·테넌트의 행이 조회되지 않음**
- [ ] 자주 쓰는 조회 조건에 인덱스가 있음 (필요하면 `EXPLAIN` 확인)
- [ ] 기존 데이터가 있는 테이블의 변경은 백필·기본값 계획이 있음
- [ ] 스키마에서 파생되는 것(타입, ORM 모델, 클라이언트)을 재생성

### C-3. 프론트엔드

**산출물에 적을 것**

- `<페이지 경로>` — 화면 이름과 접근 조건
- `<컴포넌트 경로>` — 컴포넌트 이름과 역할
- `<API 클라이언트 / 쿼리 훅 경로>` — 어떤 엔드포인트를 부르는지
- 상태 관리 위치 (서버 상태 / URL / 로컬)
- 새로 설치한 패키지와 도입 이유

**완료 기준 후보**

- [ ] 핵심 사용자 흐름이 처음부터 끝까지 동작 (E2E 시나리오로 기록)
- [ ] **로딩 · 빈 상태 · 오류 상태**가 각각 화면으로 존재
- [ ] 폼 검증 오류와 서버 오류가 사용자 언어로 안내됨
- [ ] 권한 없는 사용자에게 버튼이 보이지 않고, **직접 URL 로 들어가도 막힘**
- [ ] 모바일 폭(375px)에서 가로 스크롤 없이 읽힘
- [ ] 라이트·다크 모드에서 색이 깨지지 않음 (시맨틱 토큰만 사용)
- [ ] 키보드로 조작 가능하고 대비가 WCAG AA(4.5:1) 이상
- [ ] 변경 후 화면이 최신 데이터로 갱신됨 (캐시 무효화)
- [ ] lint · typecheck · test · **build** 통과

### C-4. 인증 · 권한

- [ ] 가입 · 로그인 · 로그아웃 · 비밀번호 재설정 흐름 동작
- [ ] 미로그인 상태로 보호 경로 접근 → 로그인으로 이동 후 **원래 가려던 곳으로 복귀**
- [ ] 리다이렉트 대상이 검증됨 (외부 주소로 튕기지 않음)
- [ ] 토큰 만료·갱신·폐기가 동작
- [ ] 역할별 허용/거부 표를 만들고 **모든 칸을 실제로 시도**해 기록
- [ ] 비밀 값이 코드·로그·클라이언트 번들에 없음

### C-5. AI · LLM · Agent

**산출물에 적을 것**

- 프롬프트 파일 위치와 버전, 모델 이름, 주요 파라미터
- 체인·그래프 구조 (노드, 상태, 분기 조건)
- 도구(tool) 목록과 각 도구의 입력·출력 스키마
- RAG 라면: 문서 출처, 청킹 규칙, 임베딩 모델, 인덱스 위치
- 평가 세트 위치 (`evals/<이름>.jsonl` 등)

**완료 기준 후보**

- [ ] 평가 세트 <n>건 중 <기준>% 이상 통과 (기준과 채점 방법을 적는다)
- [ ] 출력이 스키마를 따름 (구조화 출력 검증, 실패 시 재시도 또는 폴백)
- [ ] 근거 없는 질문에는 "모른다"고 답함 (RAG 근거 인용 확인)
- [ ] 타임아웃 · 재시도 · 레이트 리밋 처리가 있음
- [ ] 호출당 토큰·비용·지연 시간이 기록됨 (트레이싱)
- [ ] 반복 상한이 있음 (Agent 루프가 무한히 돌지 않음)
- [ ] 프롬프트 주입·민감 정보 유출 시나리오를 시도해 봄

### C-6. 인프라 · 배포 · 품질 도구

- [ ] 로컬 실행 방법이 README 한 곳에 있고 그대로 따라 하면 뜸
- [ ] 환경 변수 목록이 `.env.example` 에 있고 누락 시 시작 단계에서 실패
- [ ] CI 가 push/PR 마다 lint → 타입 체크 → 테스트 → 빌드를 수행
- [ ] 커밋 훅(pre-commit)이 포맷·lint 를 수행
- [ ] 컨테이너 이미지가 빌드되고 헬스 체크(`/health`)가 응답
- [ ] 배포 후 되돌리는 방법이 적혀 있음
- [ ] 오류 추적·로그·기본 지표가 수집됨

### C-7. 문서 · 정리

- [ ] 지운 파일을 참조하는 import 0건 (빌드로 확인)
- [ ] **코드와 함께 바뀐 문서를 전부 고침** (README, CLAUDE.md, 가이드, PRD)
- [ ] 메타 정보(서비스명, 설명, 라이선스)가 프로젝트 기준으로 바뀜

## D. 작성 원칙

### D-1. Phase 를 나누는 법

- **수직 슬라이스로 나눈다.** "DB 전부 → API 전부 → 화면 전부"가 아니라, 기능 하나를 DB 부터 화면까지 관통해 눈으로 확인할 수 있는 단위로 자른다.
- 표준 순서: **Phase 0 기반**(인증, 품질 도구, 공통 유틸) → **핵심 도메인 Phase 들** → **마무리·검증**(디자인 마감, 잔재 정리, 통합 테스트) → **2차 로드맵**(MVP 밖).
- 각 Phase 머리에 "이 Phase 가 끝나면 무엇이 가능해지는가"를 한 문장으로 적는다.
- 순서가 고정인 구간과 병렬 가능한 구간을 의존성 그림으로 구분한다. 고정인 이유도 적는다.

### D-2. Task 를 쓰는 법

- **산출물은 파일 경로로 적는다.** "회원 기능 구현"이 아니라 `app/api/users/router.py — 가입·조회·수정`.
- **완료 기준은 관찰 가능한 동작으로 적는다.** "잘 동작함"이 아니라 "같은 링크를 두 번 눌러도 에러 없음".
- **부정 테스트를 반드시 넣는다.** 권한이 걸린 Task 는 "누가 무엇을 시도하면 거부되는가"를 굵게 적는다. 되어야 하는 일만 확인하면 구멍은 보이지 않는다.
- **설계 결정에는 이유를 붙인다.** "두 테이블을 합치지 않는다 — 합치면 본인이 자기 출석을 체크할 수 있다"처럼 쓴다.
- **일부러 하지 않는 것도 적는다.** "이 패키지는 여기서 설치하지 않는다, Task 0NN 에서 도입"처럼 범위를 잘라 둔다.
- Task 하나는 한 번의 작업 세션에서 끝나고 검증 명령을 통과할 수 있는 크기로 잡는다.

### D-3. 기록을 남기는 법

- **원문을 지우지 않는다.** 전제가 바뀌면 `**YYYY-MM-DD 메모**:` 를 덧붙이고, 폐기한 산출물은 ~~취소선~~으로 남긴 뒤 어디로 옮겼는지 적는다.
- **못 한 검증은 ⚠️ 로 솔직하게 적는다.** 계획대로 확인하지 못했다면 무엇을 못 했고, 대신 무엇으로 확인했고, 재현 방법이 어디 있는지 적는다.
- 측정값은 숫자로 남긴다 (대비 4.53:1, 가로 넘침 355px → 0px, 응답 시간 p95 등).
- 바뀐 명령·절차는 옛 기록 옆에 "지금은 ○○ 을 쓴다"를 적는다.

### D-4. 숫자를 맞추는 법

- 로드맵을 고칠 때마다 세 곳을 함께 고친다: **최종 업데이트 줄**, **진행 상황 줄**, **Phase 요약표**.
- 진행률 = 완료 Task 수 ÷ 본 로드맵 Task 수. 체크박스를 직접 세어 맞춘다.
- 기능 ID(`F0xx`)는 PRD 와 일치해야 한다. 로드맵에서 기능이 늘면 PRD 도 같은 Task 안에서 고친다.

### D-5. 후속 로드맵 (2차 이후)

MVP 이후의 묶음 작업은 본 로드맵에 끼워 넣지 않고 별도 파일로 뺍니다.

- 파일명: `docs/ROADMAP<번호>-<주제>.md` (예: `ROADMAP2-UI-Polish.md`, `ROADMAP3-Search-API.md`)
- Task 번호는 **접두 문자 + 두 자리 숫자**로 따로 매긴다 (예: `Q01`–`Q15`, `P01`–`P11`). 본 로드맵 번호와 섞지 않는다.
- 본 로드맵 요약표에 한 줄을 추가하되 **합계에는 넣지 않는다**고 적는다.
- 그 줄에 적을 것: 파일 경로, 추가·보강하는 기능 ID, Task 범위, 완료 수, 상태와 날짜.
- 본 로드맵의 기존 Task 를 대체한다면 양쪽에 서로를 가리키는 문장을 적는다 ("Task 020 은 ROADMAP5 P05–P08 로 대체").

### D-6. 위험 요소 표를 쓰는 법

- "일정이 밀릴 수 있음" 같은 일반론은 쓰지 않는다. **이 스택에서 실제로 밟는 함정**을 적는다.
- 세 칸을 모두 채운다: 무슨 일이 일어나는가 / 터지면 무엇이 망가지는가 / 어떻게 막고 어느 Task 에서 확인하는가.
- 후보: 권한 검사 누락, 타임존·날짜 변환, 스키마 변경 후 파생물 재생성 누락, 메이저 버전 문법 혼입, 외부 API 한도·비용, 비동기 블로킹 호출, 캐시 무효화 누락, 비밀 값 노출.

## F. 최종 점검표

로드맵을 저장하기 전에 확인합니다.

- [ ] 최종 업데이트 줄 · 진행 상황 줄 · 요약표의 숫자가 체크박스 개수와 일치한다
- [ ] 모든 Task 에 기능 ID, 산출물(파일 경로), 완료 기준이 있다
- [ ] 권한이 걸린 Task 마다 부정 테스트가 하나 이상 있다
- [ ] 모든 구현 Task 의 마지막 완료 기준이 검증 명령 통과다
- [ ] 스키마를 바꾸는 Task 에 파생물 재생성이 적혀 있다
- [ ] 의존성 그림이 Task 의 "의존성" 줄과 어긋나지 않는다
- [ ] 2차 로드맵 항목이 MVP Phase 에 섞여 있지 않다
- [ ] 위험 요소마다 대응과 확인 Task 가 적혀 있다
- [ ] PRD 의 기능 ID 범위와 로드맵이 일치한다
