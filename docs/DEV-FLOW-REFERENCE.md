# 개발 플로우 레퍼런스 (범용)

> **이 문서의 목적**
> Claude Code로 프로젝트를 **빈 저장소에서 배포까지** 끌고 가는 방식을, 프로젝트 성격(웹 · API 서버 · CLI · 데이터 파이프라인 · AI Agent)과 상관없이 다시 쓸 수 있게 정리한 교본입니다. 회고록이 아니라 **새 프로젝트 첫날에 열어 놓고 따라가는 문서**입니다.

> **읽는 법**
> - 급하면 **0장 치트시트만** 봅니다.
> - 각 장은 **원칙 → 체크리스트 / 복붙 프롬프트** 순서입니다. `<꺾쇠>`는 프로젝트에 맞게 바꿉니다.
> - "사례"로 표시한 문단은 이 방식이 만들어진 실제 프로젝트(Next.js 블로그, 4일 42커밋)의 기록입니다. 원칙의 근거로 남겨 둔 것이니 스택이 달라도 읽어 둘 가치가 있습니다.
> - 스택별로 바꿔 끼울 것은 **11장**에 모았습니다.

> **이 문서가 담지 않는 것**
> 특정 프레임워크의 사용법, 저장소별 금지 사항(그것은 각 저장소의 `CLAUDE.md` 몫), 로드맵 양식의 세부(`ROADMAP-REFERENCE.md` 몫).

## 0장 · 한 페이지 치트시트

### 전체 흐름 (빈 저장소 → 배포)

```
[0] 준비        저장소 · settings 3계층 · MCP 등록
                 └ 산출물: .claude/settings.json, .mcp.json, CLAUDE.md 초안
                      ↓
[1] 기획        아이디어 → (린 캔버스) → PRD     (prd-generator → prd-validator)
                 └ 산출물: docs/PRD.md
                      ↓
[2] 계획        PRD → ROADMAP                   (dev-planner)
                 └ 산출물: docs/ROADMAP.md (Phase 분할 + Task 목록)
                      ↓
[3] 태스크화    ROADMAP → 실행 가능한 Task       (태스크 관리 도구)
                 └ 산출물: Task마다 완료 판정 기준
                      ↓
[4] 구현 루프   ┌──────────────────────────────────────┐
                │ 탐색 → 계획 → 구현 → 검증 → 마감      │  ← Task 하나마다 반복
                └──────────────────────────────────────┘
                      ↓
[5] 트러블슈팅  증상 → 원인 분해 → 실측 → 최소 수정 → 회귀 장치
                      ↓
[6] 마무리      통합 검증 문서 → 배포 → 배포 환경 재검증 → 로드맵 다음 버전
```

### Task 하나를 처리하는 4박자 (+마감)

| 박자 | 하는 일 | 주로 쓰는 것 |
| --- | --- | --- |
| ① 탐색 | **이미 있는 것을 먼저 찾는다.** "아직 코드는 작성하지 마"를 함께 지시 | 탐색 서브에이전트, Grep/Read, 문서 조회 MCP |
| ② 계획 | 플랜 모드에서 설계하고 파일로 남긴다 | 플랜 모드, `.claude/plans/` |
| ③ 구현 | 명세대로 짜고, 단계마다 멈춘다 | 구현 서브에이전트 또는 메인 스레드 |
| ④ 검증 | **빌드 + 린트 + 실제 실행 + 숫자** | `<검증 명령>`, `code-reviewer`, `e2e-verifier` |
| ⑤ 마감 | 태스크 상태 · 문서 · 커밋을 함께 닫는다 | 태스크 완료 처리 → `/update-mds` → 커밋 |

### 절대 잊지 말 것 7가지

1. **검증은 눈이 아니라 숫자로 한다.** 빌드 · 타입 체크 · 린트를 전부 통과한 채 살아 있는 결함이 있다.
2. **탐색 단계에서는 "아직 코드를 작성하지 말라"고 못 박는다.** 안 그러면 AI는 조사를 건너뛰고 바로 코딩한다.
3. **문서는 코드와 같은 리듬으로 갱신한다.** 문서가 밀리면 다음 세션의 AI가 틀린 전제로 코딩한다.
4. **금지 규칙에는 근거를 함께 적는다.** 근거 없는 금지는 다음 사람(과 다음 세션의 AI)이 지운다.
5. **되돌리기 어려운 작업은 드라이런으로 전량 대조한 뒤 필요한 것만 실행한다.**
6. **자동화(에이전트 · 훅)는 첫날에 다 만들지 않는다.** 같은 일을 세 번째 할 때 만든다.
7. **컨텍스트는 자원이다.** AI가 갑자기 규칙을 어기면 `/context`부터 확인하고, 작업 단위마다 `/clear`한다.

## 1장 · 전체 지도

### 1-1. 표준 Phase

| Phase | 하는 일 | 왜 여기서 끊는가 |
| --- | --- | --- |
| 0 기획 | `CLAUDE.md` 초안 → PRD → ROADMAP | 무엇을 만들고 무엇을 안 만드는지 먼저 정한다 |
| 1 골격 | 스타터 잔재 제거, 기반 세팅(타입, 환경변수 검증, 품질 도구) | 필요 없는 것을 먼저 지워야 AI가 헷갈리지 않는다 |
| 2 인터페이스 | 더미 데이터로 화면 · 엔드포인트 · 명령의 겉모습 완성 | 데이터가 없어도 겉은 만들 수 있다 |
| 3 핵심 | 실데이터 연동, 핵심 로직, 통합 검증 | 여기가 진짜 프로젝트 |
| 4 완성도 | 캐시, 검색, 부가 기능 | 핵심이 돌아간 뒤에 붙인다 |
| 5 마감 | 디자인 · 문서 마감, 배포, 배포 환경 재검증 | 마지막에 몰아서 |

권한 · 데이터 무결성이 핵심인 프로젝트는 2~3을 합쳐 **기능 하나씩 DB부터 화면까지 관통(수직 슬라이스)** 하는 편이 낫습니다. 어느 쪽이든 **첫 Phase는 "지우기와 뼈대", 마지막은 "검증과 배포"** 입니다.

### 1-2. 이 흐름에서 지킬 것 세 가지

**① 겉모습 문제와 데이터 문제를 섞지 않는다.** 더미 데이터로 겉을 먼저 완성하고 실데이터를 나중에 꽂으면, 그 뒤에 무언가 깨졌을 때 범인은 데이터 쪽으로 좁혀집니다. 둘을 동시에 하면 매번 "내 코드 문제인가, 들어온 데이터 문제인가"를 가려야 합니다.

**② 기능 커밋과 문서 커밋이 짝을 이룬다.** Claude Code는 세션이 바뀌면 대화 기억이 사라지고 문서만 남습니다. "기능 하나 = 커밋 두 개(기능 + 문서)"를 리듬으로 삼습니다.

> 사례: 42커밋 중 문서 커밋이 13건(31%)이었고, 기능 커밋 바로 뒤에 규칙적으로 붙어 있었습니다.

**③ 자동화 장치도 디버깅 대상이다.** 훅과 서브에이전트를 만들면 그 설정 자체가 버그를 냅니다(9장의 함정 목록).

> 사례: 버그 6건 중 3건이 코드가 아니라 훅 · 에이전트 설정의 버그였습니다.

### 1-3. 단계별 "끝났다"의 기준

| 단계 | 완료 조건 |
| --- | --- |
| 0 준비 | 프로젝트에서 Claude Code가 뜨고, MCP가 붙고, 첫 커밋이 있다 |
| 1 기획 | **"이 프로젝트가 검증할 단 하나의 질문"** 이 PRD 맨 앞에 있다 |
| 2 계획 | 모든 기능 ID가 **어느 Task가 담당하는지** 표로 매핑돼 있다 |
| 3 태스크화 | Task마다 **완료 판정 기준**이 있다 |
| 4 구현 | 검증 명령 통과 + 실제 실행 확인 + 리뷰 완료 |
| 5 트러블슈팅 | 원인을 **숫자로** 특정했고 **재발 방지 장치**를 남겼다 |
| 6 마무리 | 배포된 **공개 주소에서** 검증을 다시 했다 |

## 2장 · [0단계] 준비

코드를 쓰기 전에 **"AI가 이 저장소에서 어떻게 행동할지"** 를 정합니다. 안 하면 매 세션 같은 설명을 반복하고, AI는 매번 조금씩 다르게 코드를 씁니다.

### 2-1. settings는 3계층으로 나눈다

```
~/.claude/settings.json              ← ① 나 (모든 프로젝트 공통)
   model, 기본 권한 모드, language, outputStyle, 전역 권한

프로젝트/.claude/settings.json        ← ② 저장소 (git 추적, 다른 PC의 나와 공유)
   훅 등록

프로젝트/.claude/settings.local.json  ← ③ 이 PC (gitignore)
   permissions.allow, 켤 MCP 서버
```

- **기본 권한 모드를 plan으로 두는 것을 권합니다.** 플랜 모드에서는 AI가 파일을 고치지 못하고, 계획을 보여 준 뒤 승인을 받아야 손을 댑니다. "잘 알아들었겠지" 하고 맡겼다가 엉뚱한 파일 10개가 바뀌는 사고를 구조적으로 막습니다.
- **훅은 반드시 `.claude/settings.json`에 등록합니다.** `settings.local.json`은 gitignore 대상이라 여기에 등록하면 다른 PC에서는 스크립트만 있고 아무도 실행하지 않습니다.
- 설정 키 이름과 단축키는 Claude Code 버전에 따라 바뀔 수 있으니 공식 문서(참고 자료)로 확인합니다.

### 2-2. 권한은 `deny`가 최우선

```
1. deny    ← 항상 차단. allow에 있어도 deny면 차단
2. allow   ← 자동 허용
3. ask     ← 사용자 확인
4. (없음)  ← 기본값: 물어봄
```

```json
{
  "permissions": {
    "deny": ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)", "Bash(rm:*)"],
    "allow": ["Bash(<검증 명령>)", "Bash(git status)"],
    "ask": ["Bash(git push:*)"]
  }
}
```

- 최소 권한: 필요한 것만 `allow`에 넣습니다. 새 프로젝트에서는 `deny`부터 채웁니다.
- `Bash` 패턴은 접두사 매칭이라 우회할 수 있습니다. 보안 장치가 아니라 **실수 방지 장치**로 봅니다.
- 반복 작업이 확실할 때만 편집 자동 승인으로 내려가고, 모르는 영역에 들어갈 때는 plan으로 올라갑니다.

### 2-3. MCP 서버는 역할별로 붙인다

| 역할 | 예 | 쓰이는 단계 |
| --- | --- | --- |
| 라이브러리 최신 문서 조회 | `context7` | 구현(기억에 의존하지 않기 위해) |
| 복잡한 설계를 단계로 쪼개 생각 | `sequential-thinking` | 기획 · 계획 · 트러블슈팅 |
| Task 생성 · 상태 관리 | `shrimp-task-manager` 등 | 태스크화 · 구현 |
| 실제 실행 검증 | `playwright`(웹) | 검증 · 마무리 |
| 스택 전용 | UI 레지스트리, DB, 배포 서비스 MCP | 해당 스택일 때만 |

`--scope project`로 붙이면 `.mcp.json`에 기록되어 저장소를 따라다닙니다. 단, 로컬 절대 경로를 참조하는 서버는 다른 PC에서 동작하지 않습니다.

> **문서 조회 수단은 반드시 붙입니다.** AI의 학습 데이터는 시점이 고정돼 있어, 최신 버전에서 사라지거나 바뀐 API를 자신 있게 알려 줍니다. "라이브러리 이야기가 나오면 기억 대신 문서를 읽는다"를 규칙으로 둡니다.

### 2-4. `/init`은 규칙과 함께 지시한다

```text
/init 프로젝트 초기화를 한국어로 진행해주세요.
다음을 CLAUDE.md에 포함해주세요:

## 언어 및 커뮤니케이션 규칙
- 기본 응답 언어: 한국어
- 코드 주석 · 커밋 메시지 · 문서: 한국어
- 변수명/함수명: 영어 (그 언어의 표준 표기)
```

출력 스타일(`~/.claude/output-styles/<이름>.md`)로 설명 톤을 고정할 수 있습니다. 만들 때 `keep-coding-instructions: true`를 빠뜨리면 코딩 관련 기본 지침이 빠지니 주의합니다.

### 2-5. `.gitignore`에 AI 도구 산출물을 막아 둔다

```gitignore
# 개인 권한 설정
.claude/settings.local.json
# 계획 파일을 저장소 자산으로 보지 않는다면
.claude/plans
# 브라우저 검증 MCP가 남기는 로그 · 스냅샷
.playwright-mcp/
# 태스크 관리 MCP의 로컬 상태
shrimp_data/
# 훅 로그
.claude/hooks/*.log
# 스크립트 드라이런 산출물
<드라이런 출력 경로>
```

계획 · 인수인계 파일을 저장소에 남기고 싶다면 `.claude/plans`는 빼지 않습니다. 어느 쪽이든 첫날에 정합니다.

### 2-6. 0단계 체크리스트

- [ ] `git init` + 첫 커밋
- [ ] 홈 settings의 기본 권한 모드 · 언어 · 모델 확인
- [ ] `.mcp.json`에 필요한 MCP 등록, 이 PC에서 켜기
- [ ] `.gitignore`에 위 항목 추가
- [ ] `/init`으로 `CLAUDE.md` **초안만** 생성. 자세한 규칙은 실패하면서 채운다
- [ ] 예시 환경 파일(`.env.example`) 생성. 실제 값은 커밋하지 않는다
- [ ] 서브에이전트를 미리 여러 개 만들지 않는다(9-6)

## 3장 · [1단계] 기획 — 아이디어를 PRD로

**PRD**는 "무엇을 만들 것인가"를 적은 주문서입니다. AI에게 "블로그 만들어줘"라고 하면 자기가 아는 가장 흔한 블로그를 만듭니다(로그인, 관리자 화면, 댓글이 딸려 옵니다). PRD는 **"이건 안 만든다"를 명시하는 문서**이기도 합니다.

### 3-1. PRD 앞에 한 장 — 린 캔버스

아이디어가 흐릿하면 PRD 전에 린 캔버스(`LEANCANVAS-TEMPLATE.md`)로 한 장에 압축합니다. 개인 프로젝트라면 **문제 · 고객 · 핵심 지표** 세 칸이면 충분합니다. 핵심 지표 칸이 PRD의 "검증할 단 하나의 질문"으로 이어집니다.

### 3-2. PRD에 반드시 넣을 세 가지

**① 검증할 단 하나의 질문을 맨 앞에.** 기능이 많아 보여도 이 질문에 답하면 성공입니다. 개발 중 "이 기능 넣을까"가 고민될 때 **"그것이 이 질문에 답하는 데 필요한가"** 로 잘라냅니다. 프로젝트가 끝나면 **같은 자리에 실측값으로 답을 적습니다.** PRD는 살아 있는 문서입니다.

**② 안 만들 것과 그 이유.** "이미 있으니까 쓰자"는 가장 흔한 범위 확장 경로입니다. 스타터킷에 인증 화면이 있어도 그것이 있다는 이유만으로 MVP에 넣지 않는다고 적어 두면 AI도 사람도 흔들리지 않습니다.

**③ 제약과 대응.** 새 기술 · 외부 서비스를 쓴다면 **"이것을 쓰면 반드시 겪는 문제 3~5가지"** 를 조사해 요구사항으로 만듭니다(호출 한도, 만료되는 주소, 총 개수를 주지 않는 API 등). 검색어는 `"<기술명> limitations"`, `"<기술명> gotchas"`, `"<기술명> rate limit"`.

### 3-3. 순서

```
① 초안    prd-generator에게 아이디어를 설명
② 검증    prd-validator로 기술적으로 불가능하거나 위험한 요구를 골라냄
③ 흡수    검증 결과와 구조적 제약을 요구사항으로 편입
④ 확정    docs/PRD.md 커밋
```

### 3-4. 복붙 프롬프트

```text
prd-generator 서브에이전트로 PRD 초안을 만들어줘.

[아이디어]
(무엇을 만들고 싶은지 3~5문장)

[꼭 지킬 것]
- 검증할 "단 하나의 질문"을 문서 맨 앞에 적을 것
- MVP에 넣지 않을 기능과 그 이유를 별도 절로 적을 것
- 이 기술 스택/외부 서비스를 쓸 때 반드시 부딪히는 구조적 제약을 조사해
  "제약과 대응" 절로 만들 것
- 사용자 여정을 흐름도로 그릴 것
- 화면(또는 리소스 · 명령)별로 역할 · 진입 경로 · 주요 기능 · 다음 이동을 표로 정리할 것

초안이 나오면 prd-validator로 기술 검증까지 이어서 받아줘.
```

### 3-5. 체크리스트

- [ ] 검증할 단 하나의 질문이 맨 앞에 있다
- [ ] 안 만들 것 목록과 이유가 있다
- [ ] 쓸 기술 · 서비스의 구조적 제약이 조사돼 있다
- [ ] 데이터 모델과 화면(리소스 · 명령) 목록이 있다
- [ ] 문서 커밋으로 남겼다

## 4장 · [2단계] 계획 — PRD를 ROADMAP으로

| | PRD | ROADMAP |
| --- | --- | --- |
| 답하는 질문 | **무엇을** 만드는가 | **어떤 순서로** 만드는가 |
| 단위 | 기능(F001 …) | Phase와 Task |
| 바뀌는가 | 거의 안 바뀜 | 자주 바뀜(진행 상태 반영) |
| 담당 에이전트 | `prd-generator` | `dev-planner` |

양식은 `ROADMAP-REFERENCE.md`를 따릅니다. 아래는 그 양식에서 특히 빠뜨리기 쉬운 것입니다.

### 4-1. ROADMAP에 반드시 넣을 표 세 가지

**① 제약 → 담당 Task.** PRD에서 조사한 제약을 실제로 누가 처리하는지. 없으면 제약은 적어만 놓고 잊는 문서가 됩니다.

**② 기능 ID ↔ Task 커버리지.** 빠뜨린 기능을 막바지에 발견하는 사고를 막습니다.

**③ 명세와 달라진 지점.**

```markdown
| 명세 | 실제 | 이유 |
| --- | --- | --- |
| <처음 계획> | <실제로 한 것> | <실측으로 확인한 이유> |
```

계획은 **가설**입니다. 만들어 보면 절반은 틀립니다. 틀린 계획을 지우고 덮어쓰면 다음 사람(과 다음 세션의 AI)이 똑같이 잘못된 길을 다시 갑니다. **지우지 말고 취소선 + 이유로 남깁니다.**

### 4-2. 복붙 프롬프트

```text
dev-planner 서브에이전트로 docs/ROADMAP.md를 작성해줘.

근거: docs/PRD.md  (양식: docs/ROADMAP-REFERENCE.md가 있으면 그것)

[구조]
1. 개요 — 기능을 기능 ID와 함께
2. 이 프로젝트에 없는 것(인증, DB, 테스트 프레임워크 등)을 명시해 불필요한 Task를 막기
3. PRD의 제약 → 담당 Task 표
4. 개발 워크플로우 (Task 하나를 어떻게 처리하는지)
5. Phase와 Task — Task마다 관련 기능 ID / 산출물(파일 경로) / 완료 기준(부정 테스트 포함)
6. 기능 ID ↔ Task 커버리지 표
7. 검증 명령 표

[원칙]
- 첫 Phase는 "지우기와 뼈대"로 잡을 것
- 데이터 연동이 필요한 기능은 더미 단계와 실데이터 단계를 나눌지,
  기능 단위로 관통할지 정하고 이유를 적을 것
- 계획이 뒤집히면 지우지 말고 취소선으로 보존한다는 규칙을 문서에 명시할 것
```

### 4-3. 체크리스트

- [ ] Phase가 "준비 → 겉 → 핵심 → 완성도 → 마감" 또는 수직 슬라이스로 나뉘어 있다
- [ ] 모든 기능과 제약에 담당 Task가 있다
- [ ] Task마다 완료 기준이 있다("만들었다"가 아니라 "이것이 되면 끝")
- [ ] 검증 명령이 문서에 있다

## 5장 · [3단계] 태스크화

ROADMAP은 사람이 읽는 문서입니다. AI가 "지금 무슨 일을 하는 중인지" 추적하려면 **상태를 가진 데이터**가 필요합니다. 태스크 관리 MCP(Shrimp Task Manager, Claude Task Master 등)나 Claude Code의 작업 목록을 씁니다. 어느 것이든 **하나를 정해 끝까지 그것만** 씁니다. 상태가 두 곳에 나뉘면 어느 쪽도 믿을 수 없게 됩니다.

### 5-1. Task에 꼭 있어야 하는 것

| 항목 | 뜻 |
| --- | --- |
| 무엇을 하는가 | 이름과 설명 |
| 의존성 | 어떤 Task가 끝나야 시작할 수 있는가 |
| 관련 파일 | 무엇을 만들고 고치는가 |
| **완료 판정 기준** | **무엇이 되면 끝인가** ← 가장 중요 |
| 상태 | 대기 / 진행 중 / 완료 |

**크기 기준**: 한 번에 집중해서 끝낼 수 있고(커밋 1~2개), 끝났는지 스스로 판정할 수 있는 크기. 판정 기준을 못 적겠으면 그 Task는 너무 큽니다.

### 5-2. 지킬 것

- **시작할 때 "진행 중", 끝날 때 "완료"를 직접 찍습니다.** 태스크 도구는 git 변경을 감지하지 않습니다. 코드를 아무리 커밋해도 상태는 저절로 바뀌지 않습니다.
- **Task 명세는 한 곳에만 둡니다.** 권장 배치:
  - Task 명세 → 태스크 도구(단일 진실 공급원)
  - 진행 상태 요약 → `docs/ROADMAP.md`의 완료 표시
  - 검증 결과 → `tasks/NNN-*.md` 같은 파일(표와 근거가 길어 파일이 필요한 것만)

> 사례: "Task마다 `tasks/XXX.md`를 만든다"는 규칙이 있었지만 19개 중 1개만 만들어졌습니다. 태스크 도구에 같은 내용이 이미 들어가기 때문입니다. **규칙이 계속 안 지켜지면 사람이 게으른 것이 아니라 규칙이 틀린 것입니다.** 강제할 방법을 찾기 전에 그 규칙이 값을 만드는지 확인합니다.

### 5-3. 체크리스트

- [ ] 모든 Task에 완료 판정 기준이 있다
- [ ] 의존 관계가 정리돼 있다
- [ ] 시작 · 완료 처리를 규칙 문서에 적었다

## 6장 · [4단계] 구현 루프 — 이 문서의 심장

프로젝트가 웹이든 CLI든 파이프라인이든 Task 하나를 처리하는 루프는 같습니다.

```
   ① 탐색 ──→ ② 계획 ──→ ③ 구현 ──→ ④ 검증 ──→ ⑤ 마감 ──→ 다음 Task
        │                      ↑          │
        │                      └──────────┘  검증 실패 시 되돌아감
        └── "이미 있다"를 발견하면 구현 자체가 사라진다 (최고의 결과)
```

### 6-1. ① 탐색 — 만들기 전에 찾는다

AI는 시키면 무엇이든 새로 만듭니다. 방치하면 같은 기능이 세 군데에 생깁니다.

- `CLAUDE.md`에 **"이미 있는 것 목록"** 을 둡니다(공용 컴포넌트, 유틸리티, 헬퍼, 클라이언트).
- **"아직 코드는 작성하지 마"를 명시합니다.** 플랜 모드면 구조적으로 강제되고, 아니면 말로라도 금지합니다.

  ```text
  관련 파일을 읽고 현재 구조를 파악해줘.
  단, 아직 코드는 작성하지 마.
  ```

- **조사는 서브에이전트에 위임합니다.** 읽은 파일 전체가 아니라 결론만 돌아오므로 메인 컨텍스트를 아낍니다. 여러 개를 동시에 띄울 때는 **각자 다른 영역**을 줍니다. 같은 파일을 둘이 읽으면 같은 답이 두 번 옵니다.
- 라이브러리 사용법은 문서 조회 수단으로 확인합니다.

### 6-2. ② 계획 — 플랜 모드에서 설계하고 파일로 남긴다

플랜 모드에서 탐색 → 설계안 → 모호한 것은 질문 → 승인 순서로 진행합니다. 더 깊은 사고가 필요한 것은 복잡한 계획과 난해한 버그뿐입니다. 단순 구현에 요구하면 토큰만 씁니다.

**계획 파일**은 `.claude/plans/plan-YYYY-MM-DD-<기능명>.md`로 남깁니다. 기록용이 아니라 **되돌아갈 체크포인트**입니다. 구현이 꼬였을 때 처음부터 다시 생각하지 않아도 됩니다.

**세션 인수인계(handoff).** 세션이 끝나면 대화 기억이 사라집니다. 세션이 길어지면 다음 세션에게 쓰는 문서를 남깁니다. 넣을 것 네 가지:

1. 지금 어디까지 했나(태스크 상태를 도구로 실제 조회해서)
2. 다음에 무엇을 해야 하나(구체적인 명령 · ID까지)
3. **이번에 알아낸 사실** ← 가장 중요
4. 함정과 막힌 지점

끝난 인수인계 문서는 지우지 말고 맨 위에 "지난 기록입니다. 지금 상태는 ○○을 보세요"라고 적습니다.

### 6-3. ③ 구현 — 명세대로, 단계마다 멈춘다

- **각 단계가 끝나면 멈추고 다음 지시를 기다립니다.** 5개를 한 번에 시키면 3번째에서 방향이 틀어져도 5번째까지 달립니다.
- **검증하면서 시킵니다.**

  ```text
  <기능>을 만들어줘.
  각 단계마다 멈춰서 "이 부분이 제대로 동작할까", "빠뜨린 것은 없을까"를
  확인하면서 진행해줘.
  ```

- **AI에게 결과를 볼 수단을 줍니다.** 구현 → 결과 확인 → 비교 → 수정을 2~3회 반복하면 품질이 크게 오릅니다. 웹은 스크린샷(Playwright), CLI는 실행 출력, 데이터 작업은 집계 결과 표, API는 실제 응답입니다.
- **서브에이전트 체이닝은 메인 스레드가 겁니다.** 구현 에이전트 → (메인) → 리뷰 에이전트 → (메인) → 검증 에이전트. 에이전트가 에이전트를 부르면 맥락이 얇아지고 메인은 중간에 무슨 일이 있었는지 모릅니다.

### 6-4. ④ 검증 — 눈이 아니라 숫자로 (가장 중요)

| 층 | 수단 | 잡아내는 것 | 못 잡는 것 |
| --- | --- | --- | --- |
| 1 | 빌드 · 타입 체크 | 타입 오류, 빌드 실패 | 값이 틀린 것 |
| 2 | 린트(기준선을 정해 둔다. 권장: 경고 0건) | 코드 규칙 위반 | 논리 오류 |
| 3 | 테스트(있다면) | 검증해 둔 동작의 회귀 | 테스트가 없는 영역 |
| 4 | `code-reviewer` | 설계 문제, 저장소 규칙 위반 | 실행해야 보이는 것 |
| 5 | `e2e-verifier` / 실제 실행 | 흐름, 오류 메시지, 권한 경계 | 조용히 틀린 값 |
| **6** | **전수 스크립트 · 실측 숫자** | **위가 전부 놓치는 것** | — |

> 사례: 결함 3건(본문 이미지가 썸네일 해상도, 화면 전체가 엉뚱한 글꼴, 목차가 본문을 삼킴)이 빌드 · 타입 체크 · 린트 · 육안 확인을 **전부 통과한 채** 살아 있었습니다. 전부 "화면은 멀쩡히 뜨는데 틀린" 부류였고, 잡아낸 방법은 모두 숫자 비교였습니다 — 이미지 182장의 확대율 전수 측정, 두 글꼴로 그린 문자열의 폭 비교, 글 39편의 소제목 비율 전수 측정.

**검증은 두 숫자를 비교하는 것입니다.**

- 기대값과 실제값 (39건이어야 하는데 몇 건인가)
- 정상 표본과 이상 표본 (다른 38개는 0~11%인데 이것만 96%)
- 수정 전과 수정 후 (7.68배 → 0.93배)

이 셋 중 하나로 표현할 수 없으면 검증한 것이 아닙니다.

**권한이 걸린 기능은 부정 테스트를 합니다.** "되어야 하는 일"만 확인하면 구멍이 보이지 않습니다. 두 번째 계정으로 남의 데이터 수정, 자기 권한 밖의 동작을 시도해 **거부되는 것**을 확인합니다. "바뀔 때만 검사하는" 규칙은 반드시 다른 값으로 바꾸는 시도를 대조군으로 둡니다.

**회귀 방지 장치를 남깁니다.** 테스트 프레임워크가 없어도 **"이 프로젝트에서 가장 조용히 깨지는 것"** 만 세는 전수 대조 스크립트 하나는 만들 수 있습니다(11-2).

### 6-5. ⑤ 마감 — 세 곳을 함께 닫는다

```
1) 태스크 도구   완료 처리(검증 요약과 함께)
2) 문서          /update-mds        ← ROADMAP 완료 표시, 규칙 문서
3) 커밋          기능 커밋 + 문서 커밋
```

커밋 메시지는 `<이모지> <타입>: <설명>` 형식(타입: feat / fix / docs / style / refactor / perf / test / chore), 명령형 어조, 원자적 커밋. **fix 커밋의 본문은 길게 씁니다** — 무엇이 / 왜 / 근거 실측치 / 검증 결과 순으로. 나중에 `git log --grep=fix`로 꺼내면 트러블슈팅 사례집이 됩니다.

### 6-6. 체크리스트 (Task 하나 끝낼 때마다)

- [ ] 만들기 전에 이미 있는지 찾아봤다
- [ ] 플랜 모드에서 계획하고 승인받았다
- [ ] `<검증 명령>` 통과, 기준선 유지
- [ ] `code-reviewer` 리뷰를 받았다
- [ ] 실제로 돌려 확인했다
- [ ] **숫자로** 검증했다(기대값 대 실제값), 권한이 걸렸으면 부정 테스트도
- [ ] 태스크 완료 처리 → 문서 갱신 → 커밋

## 7장 · [5단계] 트러블슈팅

### 7-1. 5단계 절차

```
① 증상을 사용자 말 그대로 적는다   (각색하지 않는다)
② 원인 후보로 분해한다             ← 원인은 하나가 아닐 수 있다
③ 실측으로 원인을 특정한다          ← 추측으로 고치지 않는다
④ 최소 수정                        ← 관련 없는 것까지 건드리지 않는다
⑤ 회귀 장치를 남긴다               ← 스크립트 또는 금지 규칙
```

②가 핵심입니다. 원인을 하나 찾으면 바로 고치고 싶어지지만, 증상 하나에 원인이 여럿(데이터 · 레이아웃 · 파싱)인 경우가 많습니다.

### 7-2. 규칙 네 가지

**① 뜬다고 맞는 것이 아니다.** "에러가 안 나니까 괜찮다"는 검증이 아닙니다.

**② 코드를 의심하기 전에 데이터를 의심한다.** 로직을 뜯는 것보다 **입력 데이터의 분포를 세는 것**이 빠릅니다. 전체 분포를 재면 이상치가 튀어나오고, 대개 그것이 원인입니다.

**③ 증상이 사라졌다고 원인을 맞힌 것이 아니다.** 무언가를 바꾼 뒤 증상이 사라져도 우연일 수 있습니다. 같은 증상이 재발하면 처음 진단을 의심하고, **오진을 정정한 기록을 남깁니다.**

**④ 되돌리기 어려운 수정은 드라이런 전량 대조부터.** 외부 시스템(DB · API · 파일)을 대량 수정하는 스크립트에는 **`--dry-run`을 먼저** 만듭니다. 전량을 변환해 결과만 파일로 받고, 의도한 것만 바뀌었는지 대조한 뒤, 바뀌어야 할 것만 골라 실제로 씁니다. DB라면 `begin; … rollback;`이 드라이런입니다.

### 7-3. 복붙 프롬프트

```text
[증상] (사용자가 말한 그대로. 각색하지 말 것)

다음 순서로 진행해줘. 추측으로 고치지 마.

1. 원인 후보를 최소 3개로 분해해줘 (코드 / 데이터 / 설정·환경)
2. 각 후보를 "어떤 숫자를 재면 확인되는지"로 바꿔줘
3. 실제로 측정해서 원인을 특정해줘
   - 전체 데이터의 분포를 세는 방법을 우선 고려
   - 화면 문제라면 계산된 값(getComputedStyle 등)을 실측
4. 최소 수정만 해줘. 관련 없는 것은 건드리지 마
5. 같은 결함이 재발하면 자동으로 걸리는 장치를 제안해줘
   (전수 대조 스크립트 또는 규칙 문서에 넣을 금지 항목)
6. 수정 전/후 숫자를 비교해서 보여줘
```

## 8장 · [6단계] 마무리 — 통합 검증과 배포

### 8-1. 통합 검증은 검증 전용 Task로

Phase가 끝나면 개별 기능이 아니라 **사용자 여정 전체**를 검증합니다. 이 Task는 **코드를 쓰지 않습니다.** 검증하면서 고치기 시작하면 무엇을 검증했는지 알 수 없게 됩니다. 발견한 결함은 문서에 기록하고 수정은 별도 커밋으로 합니다.

### 8-2. 검증 결과 문서 템플릿

```markdown
# Task NNN · 통합 검증 결과

> **검증일**: YYYY-MM-DD
> **환경**: (프로덕션 빌드 실행 / 배포 주소 / 실제 조작 방식)
> **데이터**: (실제 데이터 규모를 숫자로)

이 Task는 검증 전용이다. 발견된 결함은 여기 기록하고 수정은 별도 커밋으로 처리한다.

## 요약
| 구분 | 결과 |
| --- | --- |
| 사용자 여정 (N개 경로) | |
| 데이터 정합성 (N개 항목) | |
| 권한 경계 · 부정 테스트 (N개 항목) | |
| 엣지 케이스 (N개 항목) | |
| (웹) 반응형 375 / 768 / 1280 · 콘솔 · 네트워크 | |

**신규 결함 N건.**

## A. 사용자 여정
| 시나리오 | 결과 | 근거 |
| --- | --- | --- |

## B. 데이터 정합성
| 항목 | 결과 | 근거 |
| --- | --- | --- |
| 전체 수 = 분류별 합계 | ✅ | 39 = 19 + 8 + 12 |

## C. 권한 경계 / D. 엣지 케이스 / E. 외부 서비스 장애 시 동작

## 검증 중 발견돼 수정된 것
| 결함 | 원인 | 수정 |
| --- | --- | --- |

## 미검증으로 남긴 항목
| 항목 | 이유 | 대체 검증 |
| --- | --- | --- |
```

- **"근거" 열**: ✅만 있으면 나중에 정말 확인했는지 알 수 없습니다. 실측값을 적습니다.
- **"미검증으로 남긴 항목"**: 확인하지 못한 것을 지우지 않고 이유와 함께 보존합니다.

### 8-3. 배포하면 새로운 것이 드러난다

| 배포 환경에서 다시 볼 것 | 왜 로컬에서 못 보나 |
| --- | --- |
| 절대 주소에 localhost 흔적이 없는가 | 로컬에서는 localhost가 정답처럼 보인다 |
| 환경변수가 실제로 등록됐는가(보호 엔드포인트의 인증 응답) | 배포해야 안다 |
| 한글 · 공백이 든 경로 | 인코딩 문제는 배포 도메인에서 더 잘 드러난다 |
| 캐시 헤더 · HTTP 상태 코드 | 호스팅이 로컬 서버와 다른 값을 보낸다 |
| 세션 없이 불리는 경로(크롤러 · cron · 웹훅) | 리다이렉트로 조용히 실패한다. 로그아웃 상태에서 직접 요청해 확인 |

발견한 것을 전부 고칠 필요는 없습니다. **알고 남겨 두는 것과 모르는 것은 다릅니다.** 고치지 않기로 한 것은 문서에 남깁니다.

배포가 끝이 아닙니다. **로드맵을 다음 버전으로 잇는 것**(후속 로드맵 파일)까지가 한 사이클입니다. 자리를 비운 동안 여러 Task를 이어 돌릴 때는 `OVERNIGHT-RUN-TEMPLATE.md`를 씁니다.

### 8-4. 체크리스트

- [ ] 통합 검증을 검증 전용 Task로 분리했다
- [ ] 결과 표의 근거 열에 실측값이 있다
- [ ] 미검증 항목을 이유와 함께 보존했다
- [ ] 배포 후 공개 주소에서 같은 검증을 다시 했다
- [ ] 발견했지만 고치지 않기로 한 것을 문서에 남겼다
- [ ] PRD의 "검증할 단 하나의 질문"에 답을 적었다

## 9장 · 자동화 레퍼런스

### 9-1. 네 가지 도구의 역할

| 도구 | 무엇인가 | 언제 동작하나 | 비유 |
| --- | --- | --- | --- |
| **서브에이전트** | 특정 역할의 별도 AI | 메인 AI가 호출할 때 | 전문가를 부른다 |
| **훅** | 이벤트에 실행되는 스크립트 | 도구 사용 직전 · 직후 등 | 자동문 센서 |
| **슬래시 커맨드** | 자주 쓰는 지시를 저장한 것 | 내가 `/이름`을 칠 때 | 단축키 |
| **MCP 서버** | 외부 기능을 붙이는 연결 | 도구로 호출될 때 | 확장 플러그인 |

훅은 사람도 AI도 건너뛰지 못합니다. 나머지는 "쓸 수 있는 것"이고 훅은 "무조건 걸리는 것"입니다. 스킬(`.claude/skills/<이름>/SKILL.md`)은 상황에 맞으면 AI가 알아서 꺼내 쓰는 것입니다. **내가 타이밍을 정하고 싶으면 커맨드, AI가 판단해도 되면 스킬**입니다.

### 9-2. 서브에이전트

**공통으로 두는 것(스택 무관)**

| 이름 | 언제 | 성격 |
| --- | --- | --- |
| `prd-generator` / `prd-validator` | PRD 초안 / 기술 검증 | 기획 |
| `dev-planner` | ROADMAP 작성 · 구조 변경 | 계획 |
| `code-reviewer` | **구현 직후 자동 호출.** 코드를 고치지 않고 리뷰만 | 검토 |
| `code-refactorer` | **사용자가 명시적으로 요청했을 때만** | 검토 |
| `e2e-verifier` | 실제 실행으로 검증. 코드 수정 안 함 | 검증 |
| `domain-expert` | 분야를 인자로 받아 사실 · 코드 · 설계 검토 | 검토 |

스택 전용(구현 에이전트, 도메인 전문가)은 프로젝트마다 따로 둡니다(11-3).

**설계 원칙**

1. **고치는 에이전트와 안 고치는 에이전트를 나눕니다.** 검토자가 고치기 시작하면 무엇이 문제였는지 기록이 사라집니다.
2. **리팩터러는 "명시적 요청 시에만".** 안 그러면 버그 수정을 시켰는데 주변 코드까지 리팩터링해 놓습니다.
3. **본문 규격**: 호출 시나리오 예시 / 범위 한정("방금 바뀐 부분만") / 검토 항목 열거 / 출력 템플릿 고정 / 완료 기준.
4. 지적에는 **문제 · 영향 · 해결 방안**을 함께 적게 합니다.

**⚠️ 정의 파일 함정 네 가지**

| # | 함정 | 결과 | 해법 |
| --- | --- | --- | --- |
| 1 | `tools:` 필드를 적음 | MCP 도구가 빠져 문서 조회 · 브라우저 검증을 못 쓸 수 있다 | 필드를 생략하고 도구 제한은 본문 규칙으로. 꼭 막아야 하면 `disallowedTools` |
| 2 | `description`에 콜론+공백이 들어감 | YAML 파싱이 깨져 **에러 없이** 목록에서 빠진다 | `description: \|-` 블록 스칼라로 감싼다 |
| 3 | 정의를 고치고 바로 테스트 | 같은 세션에는 반영되지 않는다 | Claude Code를 재시작 |
| 4 | 에이전트가 다른 에이전트를 호출 | 맥락이 얇아지고 메인이 상황을 모른다 | 체이닝은 메인 스레드가 |

### 9-3. 훅

| 종류 | 이벤트 | 하는 일 |
| --- | --- | --- |
| 가드 | PreToolUse (Edit\|Write) | 쓰면 안 되는 파일명 생성, 관리 영역 직접 수정, 이 저장소에 없는 문법 사용을 **차단(exit 2)** |
| 린트 | PostToolUse (Edit\|Write) | 방금 고친 파일에 린터를 돌리고 실패하면 출력을 AI에게 되돌려 줌 |
| 알림 | Notification, Stop | 권한 요청 · 작업 완료를 메신저로 알림 |

- **`exit 2`가 차단 신호**입니다. 그냥 실패(exit 1)는 차단하지 않습니다.
- **린트 훅이 가성비가 가장 좋습니다.** 훅 하나만 만든다면 PostToolUse에 그 언어의 린터 · 포매터를 겁니다(JS/TS는 eslint, Python은 `ruff`, Go는 `go vet`, Rust는 `cargo clippy`).
- **훅은 안전망이 아니라 보조입니다.** 의존 도구(jq 등)를 못 찾으면 조용히 통과하게 짜여 있는 경우가 많습니다.
- **잡을 대상을 정확히 좁힙니다.** 파일 확장자를 보지 않고 내용만 검사하면 무관한 파일까지 막습니다.

### 9-4. 슬래시 커맨드

잘 만든 커맨드의 4단 구조(`/update-mds`가 예):

```
1단계 — 근거 수집        인자 → git 상태 → 태스크 도구
                         근거가 서로 다르면 임의로 합치지 않고 보고에 함께 적는다
2단계 — 대상별 판단      항상 검토할 것 / 조건부로 고칠 것(조건을 명시)
3단계 — 적용 방식        기준에 해당하면 바로 반영, 근거가 충돌하면 멈추고 묻는다
4단계 — 완료 보고        고정 포맷
```

설계 원칙: ① `allowed-tools`로 권한을 좁힌다(문서 갱신 커맨드가 커밋을 하면 안 된다) ② "항상"과 "조건부"를 나눈다 ③ "확신 없으면 멈춘다"를 명시한다.

만들어 두면 좋은 것: 커밋 생성(분할 제안까지), 문서 동기화(`/update-mds`).

### 9-5. CLAUDE.md

- **일반 상식과 다른 지점만 적습니다.** AI가 실수하는 이유는 몰라서가 아니라, 널리 알려진 지식이 이 저장소에서는 틀리기 때문입니다. 첫 절을 "먼저 읽을 것 — 이 저장소에서 틀리기 쉬운 N가지"로 둡니다.
- **금지 규칙의 형식**: `[금지] + [근거 실측치] + [왜 발견이 늦는지]`. 근거 없는 금지는 다음 사람이 지웁니다. "왜 발견이 늦는지"를 적으면 어겼을 때의 진짜 비용이 전달됩니다.
- **문서마다 "담지 않는 것"을 첫 문단에 선언합니다.** 중복을 막는 가장 싼 방법입니다.

  | 문서 | 독자 | 담는 것 |
  | --- | --- | --- |
  | `README.md` | 사람 | 실행 방법, 환경변수, 배포 |
  | `CLAUDE.md` | AI | 코드 수정 규칙, 아키텍처, 저장소 특화 함정 |
  | 규칙 문서(선택) | AI | 절대 금지 사항(압축된 규칙만) |
  | `docs/PRD.md` | 둘 다 | 무엇을 만드는가 |
  | `docs/ROADMAP.md` | 둘 다 | 어떤 순서로(진행 상태) |

- **두껍게 둘지 얇게 둘지**: `CLAUDE.md`는 모든 세션에 통째로 실립니다. 판단 기준은 *"이것을 모르면 코드를 망가뜨리는가"*. 그렇다면 `CLAUDE.md`에, 알면 좋은 정도면 `docs/guides/`로 빼고 필요할 때 읽게 합니다. `/context`로 실제 비용을 확인하고 정합니다.
- 프로젝트별 지식은 PC 경로에 묶인 자동 메모리보다 저장소 안의 문서에 둡니다. PC를 옮겨도 따라옵니다.

### 9-6. 자동화는 언제 늘리나

**같은 일을 세 번째 할 때** 자동화합니다. 로드맵을 쓰려는 순간에 planner를, 구현을 시작하는 순간에 구현 에이전트를, 브라우저 검증이 반복되는 순간에 검증 에이전트를 추가합니다. 첫날에 다 만들면 쓰지도 않을 것을 관리하게 됩니다.

### 9-7. 컨텍스트와 세션 위생

대화가 길어지면 앞의 내용이 요약되어 세부가 흐려집니다.

| 명령 | 언제 |
| --- | --- |
| `/context` | 수시로. 무엇이 컨텍스트를 먹고 있는지 확인 |
| `/clear` | 작업 단위가 끝났을 때 |
| `/compact` | 한 작업이 길어졌지만 맥락은 유지해야 할 때 |
| `/resume` | 중단된 세션을 이어받을 때 |

```
Task 시작 → (필요하면 /clear)
   조사는 서브에이전트에 위임
   구현 → 검증 → 커밋
Task 종료 → /context 확인 → 무거우면 /clear
세션을 접을 때 → handoff 문서 작성 (6-2)
```

컨텍스트가 부족해서 생기는 문제는 버그처럼 보이지 않습니다. AI가 아까 정한 규칙을 어기거나 이미 있는 함수를 다시 만듭니다. **그때는 `/context`를 먼저 봅니다.**

6. 금지 규칙에는 근거와 "왜 발견이 늦는지"를 함께 적는다
7. 틀린 계획을 지우지 말고 취소선으로 보존한다
8. 규칙이 계속 안 지켜지면 규칙이 틀린 것이다
9. 같은 값 · 규칙은 한 곳에만 둔다. 두 곳에 있으면 한쪽만 바뀐다

**검증**

10. "뜬다"는 검증이 아니다
11. 검증은 두 숫자를 비교하는 것이다
12. 코드보다 데이터를 먼저 의심한다
13. 증상이 사라졌다고 원인을 맞힌 것이 아니다. 오진 정정 기록을 남긴다
14. 테스트 프레임워크가 없어도 회귀 장치는 만들 수 있다
15. 권한은 되어야 하는 일과 **막혀야 하는 일**을 함께 확인한다
16. 못 한 검증은 숨기지 않고 이유와 함께 적는다

**안전**

17. 되돌리기 어려운 작업은 드라이런 전량 대조부터
18. 자동화 장치도 디버깅 대상이다
19. 프로세스를 일괄 종료하지 않는다(런타임 프로세스를 전부 죽이면 MCP 서버까지 죽는다). 포트나 PID로 특정한다
20. 실행 중인 서버 아래에서 다시 빌드하지 않는다(코드는 멀쩡한데 화면만 깨진다)
21. 비밀 값은 대화 · 커밋 · 문서에 쓰지 않는다. 있는지만 확인하고 값은 출력하지 않는다
22. 환경변수가 없을 때는 조용히 꺼지게 한다(fail-closed). 빈 값과 비교해 통과시키지 않는다

**AI와 일하는 방식**

23. 플랜 모드를 기본값으로 둔다
24. "하지 마라"가 "해라"보다 강력하다. AI는 하지 말아야 할 것을 알려 주지 않으면 모른다
25. 단계마다 멈추게 한다
26. 라이브러리는 기억이 아니라 문서로 확인한다
27. 세션 경계를 관리한다(handoff)
28. 컨텍스트는 관리해야 하는 자원이다
29. 반복이 품질을 만든다. 결과를 볼 수단을 주고 2~3회 돌린다

프로젝트가 끝나면 이 장에 새로 배운 것을 추가합니다.

## 11장 · 프로젝트 성격에 맞게 갈아 끼우기

### 11-1. 그대로 쓰는 것 / 갈아 끼우는 것

| 그대로 쓰는 것 | 갈아 끼우는 것 |
| --- | --- |
| 거시 흐름(준비 → 기획 → 계획 → 태스크 → 구현 → 트러블슈팅 → 마무리) | 스택별 함정 목록(`CLAUDE.md`의 내용) |
| 4박자 구현 루프 | 검증 명령 |
| 문서 역할 분리 | 구현 · 도메인 서브에이전트 |
| PRD의 "검증할 단 하나의 질문" | 실제 실행 검증 수단 |
| 트러블슈팅 5단계, 회귀 장치 | "이미 있는 것 목록"의 내용 |
| settings 3계층, 훅 아이디어, 커밋 2박자 | 훅에 거는 린터 |

### 11-2. 검증을 프로젝트에 맞게 설계한다

```
1층: 기계가 잡아 주는 것      → 그 언어의 빌드 · 타입 체크 · 린터 · 테스트
2층: 돌려 봐야 아는 것        → "사용자가 하는 그대로" 한 번 해 본다
3층: 위 둘이 못 잡는 것       → "가장 조용히 깨지는 것"을 찾아 숫자로 센다
```

| 프로젝트 | 1층 (검증 명령 예) | 2층 | 3층 — 가장 조용히 깨지는 것과 세는 방법 |
| --- | --- | --- | --- |
| 웹 프론트엔드 | lint + typecheck + test + **build** | 실제 브라우저(Playwright) | 죽은 링크, 깨진 앵커, 잘못 적용된 스타일 → 빌드 산출물 전수 대조, 계산된 값 실측 |
| API 서버 (FastAPI 등) | `ruff check` + 타입 체크 + `pytest` | 실제 요청(정상 · 422 · 401 · 403 · 404 · 409) | 권한 누락, 스키마와 응답의 불일치 → 역할 × 엔드포인트 허용/거부 표를 전부 시도, OpenAPI 스키마와 실제 응답 대조 |
| DB · 마이그레이션 | 적용 → 되돌리기 → 재적용 왕복 | 제약 위반 행 삽입 시도 | 다른 사용자 · 테넌트의 행이 보임 → 두 번째 계정으로 0행인지 확인 |
| 데이터 파이프라인 | 린트 + 스키마 검증 | 샘플 입력 통과 | 행 누락 · 중복 → 입력 행 수 대 출력 행 수, 키 중복 수, 필드별 결측률 |
| CLI | 린트 + 테스트 | 실제 명령 실행 | 특정 옵션 조합의 출력 깨짐 → 옵션 조합별 출력 스냅샷 비교 |
| AI · LLM · Agent | 린트 + 단위 테스트 | 실제 질문으로 대화 | 근거 없는 답, 스키마를 벗어난 출력, 끝나지 않는 루프 → 평가 세트 통과율, 구조화 출력 검증 실패 수, 반복 횟수 상한, 호출당 토큰 · 지연 기록 |
| ML 실험 | 린트 + 테스트 | 작은 데이터로 한 바퀴 | 데이터 누수, 라벨 분포 왜곡 → 학습/검증 교집합 수, 클래스 분포 |

Phase 1에서 **"이 프로젝트에서 가장 조용히 깨지는 것이 무엇인가"** 를 묻고, 그것을 세는 스크립트를 하나 만듭니다.

### 11-3. 서브에이전트 구성 예

| 프로젝트 | 구현 에이전트 | 검증 에이전트 | 도메인 에이전트 |
| --- | --- | --- | --- |
| 웹 | `<프레임워크>-developer`, 마크업 전담 | `e2e-verifier` | 쓰는 외부 서비스 전문가 |
| API 서버 | `api-developer` | `e2e-verifier`(실제 요청) | DB · 인증 전문가 |
| 데이터 파이프라인 | `pipeline-developer` | 데이터 품질 검사(스키마 · 행 수 · 분포) | 쓰는 DB · 포맷 전문가 |
| CLI | `cli-developer` | 명령 실행 후 출력 대조 | — |
| AI Agent | `agent-developer` | 평가 세트 실행 · 채점 | 프레임워크 전문가 |

공통: `code-reviewer`, `dev-planner`, `prd-generator` / `prd-validator`, 필요하면 `domain-expert`.

## 12장 · 시작 체크리스트

### 12-1. 첫날 (30분)

- [ ] `git init` → 첫 커밋
- [ ] 홈 settings 확인(기본 권한 모드, 언어, 모델)
- [ ] MCP 등록(최소: 문서 조회 + 태스크 관리 + 검증 수단)
- [ ] `.gitignore`에 AI 도구 산출물 추가
- [ ] `/init`으로 `CLAUDE.md` 초안
- [ ] 예시 환경 파일 생성

### 12-2. 첫 주

- [ ] (아이디어가 흐릿하면) 린 캔버스
- [ ] `docs/PRD.md` — 검증할 단 하나의 질문 + 안 만들 것 + 제약과 대응
- [ ] `docs/ROADMAP.md` — Phase 분할 + Task + 제약 → Task 매핑
- [ ] 태스크 도구에 Task 등록(완료 판정 기준 필수)
- [ ] "가장 조용히 깨지는 것"을 정하고 세는 스크립트 초안
- [ ] PostToolUse 훅에 그 언어의 린터 걸기

### 12-3. Task 하나 처리할 때마다

```
□ 탐색   이미 있는지 찾아봤나?
□ 계획   플랜 모드에서 승인받았나?  계획 파일을 남겼나?
□ 구현   명세대로 했나?  단계마다 멈췄나?
□ 검증   검증 명령 통과?  리뷰 받았나?  실제로 돌려 봤나?
         ⭐ 숫자로 비교했나?  (권한이 걸렸으면) 부정 테스트를 했나?
□ 마감   태스크 상태를 닫았나?  문서를 갱신했나?  커밋 2박자?
```

### 12-4. 복붙 프롬프트

**새 Task를 시작할 때**

```text
Task <번호>를 시작할게. 다음 순서로 진행해줘.

1. 먼저 이 저장소에 비슷한 구현이 이미 있는지 찾아봐.
   새로 만들기 전에 재사용할 수 있는 것부터 확인해줘. 아직 코드는 작성하지 마.
2. 외부 라이브러리를 쓴다면 현재 버전 문서를 확인해줘. 기억에 의존하지 마.
3. 계획을 세우고 승인받은 뒤에 구현해줘. 각 단계가 끝나면 멈추고 알려줘.
4. 구현 후 <검증 명령>을 돌리고, code-reviewer 리뷰를 받아줘.
5. 마지막에 "무엇을 어떤 숫자로 확인했는지"를 표로 보고해줘.
```

**Phase가 끝났을 때 (통합 검증)**

```text
Phase <N>이 끝났어. 통합 검증을 해줘. 단, 이번엔 코드를 고치지 마.
결함을 발견하면 문서에 기록만 하고, 수정은 별도로 진행할 거야.

검증 항목:
- PRD의 사용자 여정을 처음부터 끝까지 (경로별로)
- 데이터 정합성 (합계, 정렬, 중복)
- 권한 경계 (두 번째 계정으로 막혀야 하는 일을 시도)
- 엣지 케이스 (빈 데이터, 없는 항목, 잘못된 입력)
- (웹이면) 반응형 375/768/1280, 다크모드, 콘솔 에러
- 외부 서비스 장애 시 동작

결과는 tasks/<번호>-integration-test.md에 남겨줘:
- 상단에 검증일/환경/데이터 규모
- 항목별 "시나리오 | 결과 | 근거" 표 (근거에는 실측값)
- 확인 못 한 항목은 지우지 말고 "미검증으로 남긴 항목"에 이유와 함께
```

**세션을 마칠 때 (인수인계)**

```text
오늘 세션을 정리해줘. .claude/plans/handoff-YYYY-MM-DD-<주제>.md에 다음을 남겨줘.
1. 지금 어디까지 했나 (태스크 상태 포함, 도구로 실제 조회해서)
2. 다음 세션에서 바로 이어받을 방법 (구체적인 명령/ID까지)
3. 이번 세션에서 새로 알아낸 기술 사실 ← 가장 중요
4. 막혔던 지점과 함정
```
