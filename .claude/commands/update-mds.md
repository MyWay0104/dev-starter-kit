# 개발 문서 동기화 (/update-mds)

방금 또는 최근에 한 작업을 근거로, 갱신이 필요한 md 문서를 찾아 한 번에 반영한다. 어느 저장소에서든 쓸 수 있게, 문서 위치와 표기 규칙은 **그 저장소에서 찾아서** 따른다.

인자: $ARGUMENTS

**이 커맨드가 하지 않는 것**

- 커밋 · push · 브랜치 조작을 하지 않는다. 문서 수정까지만 한다.
- 태스크 관리 도구의 상태를 바꾸지 않는다(시작 · 완료 처리는 구현 작업의 몫). 조회만 한다.
- 근거 없이 새 Task를 만들어 넣지 않는다.
- 코드를 고치지 않는다.

## 0단계 — 문서 찾기

저장소 루트(`git rev-parse --show-toplevel`)에서 아래를 찾는다. 없는 것은 건너뛴다.

| 종류 | 찾는 곳 |
| --- | --- |
| 로드맵(본편) | `docs/ROADMAP.md` → 없으면 루트 `ROADMAP.md` |
| 후속 로드맵 | `docs/ROADMAP<번호>*.md` (예: `ROADMAP2-….md`, `ROADMAP4-1-….md`) |
| AI 규칙 문서 | `CLAUDE.md`, `AGENTS.md`, `shrimp-rules.md`(루트 또는 `planning/`) |
| 사람용 안내 | `README.md` |
| 요구사항 | `docs/PRD.md` |
| 그 밖 | `docs/guides/*.md`, 규칙 문서가 "함께 고치라"고 지목한 문서 |

규칙 문서에 **문서를 고치는 순서나 규칙**(예: "계획서 → PRD → ROADMAP 순으로 함께 고친다", "원문을 지우지 않는다")이 적혀 있으면 이 커맨드의 기본 동작보다 그 규칙을 우선한다.

**로드맵이 하나도 없으면** 수정하지 말고 사용자에게 알린다. 새로 만들지 물어보고, 만들기로 하면 `dev-planner` 서브에이전트(또는 `docs/ROADMAP-REFERENCE.md` 양식)로 작성하도록 안내한다. 로드맵이 없어도 2단계의 다른 문서 검토는 계속한다.

## 1단계 — 진행 상황 파악 (근거 수집)

하나만 보고 멈추지 않는다. 근거가 서로 다르면 임의로 합치지 말고 4단계 보고에 함께 적는다.

1. **인자** — `$ARGUMENTS`에 Task 번호(`004`, `004,005`, `010-1`, `Q03`)나 힌트가 있으면 가장 먼저 단서로 삼는다.
2. **git** — `git status`, `git diff HEAD`, `git log -10 --oneline`으로 실제로 바뀐 파일과 최근 커밋 메시지를 본다. 커밋 메시지나 브랜치 이름에 Task 번호가 있으면 근거로 쓴다.
3. **태스크 관리 도구** — 연결돼 있으면 조회한다(shrimp라면 `list_tasks(status: "all")`, 특정 Task가 짐작되면 `get_task_detail`). 연결돼 있지 않으면 건너뛰고 그렇다고 보고한다.
4. **로드맵의 완료 기준** — 짐작되는 Task의 완료 기준·산출물을 읽고, 바뀐 파일이 그 산출물과 맞는지 대조한다.

**판정**

| 상황 | 처리 |
| --- | --- |
| 인자 · git · 태스크 도구가 같은 Task를 가리키고 완료가 분명함 | 완료로 반영 |
| 구현은 보이지만 완료 기준 일부가 확인되지 않음 | 확인된 항목만 체크, Task 제목은 완료로 바꾸지 않음 |
| 근거가 서로 다른 Task를 가리키거나 완료 여부가 불분명함 | 수정하지 않고 3단계의 질문으로 |
| 인자도 없고 근거로도 특정되지 않음 | 미완료 Task 목록을 보여 주고 "어떤 Task를 완료했나요? (예: 004 또는 004,005)"라고 묻는다 |

## 2단계 — 문서별 갱신

### ROADMAP — 항상 검토

**먼저 그 문서의 표기 규칙을 읽는다.** "표기 규칙" 절이 있으면 그것을, 없으면 이미 완료된 Task가 어떻게 적혀 있는지를 보고 **같은 방식**으로 적는다. 한 문서에 두 표기를 섞지 않는다. 흔한 두 가지:

| | 체크박스 방식 | 제목 표시 방식 |
| --- | --- | --- |
| Task 제목(전) | `- [ ] **Task 004: 제목** - 우선순위` | `- **Task 004: 제목** - 우선순위` |
| Task 제목(후) | `- [x] **Task 004: 제목** ✅ - 완료` | `- **Task 004: 제목** ✅ - 완료` |
| 하위 항목 | `- [ ] 기준` → `- [x] 기준` | `- 항목` → `- ✅ 항목` |
| 산출물 | `- 경로 — 설명` → `- ✅ 경로 — 설명` | 같음 |

완료로 판정한 Task마다:

1. **Task 제목** — 완료 표기로 바꾼다. `- 우선순위`가 붙어 있었으면 떼고, 이미 완료 표기면 건너뛴다.
2. **하위 항목** — 실제로 확인된 완료 기준 · 산출물만 체크한다. **확인하지 못한 기준을 일괄 체크하지 않는다.** 계획대로 검증하지 못한 항목은 체크하되 바로 아래에 `⚠️ 무엇을 못 했고 대신 무엇으로 확인했는지`를 한 줄 덧붙이거나, 체크하지 않고 남긴 뒤 보고에 적는다.
3. **다음 우선순위** — 방금 완료한 Task에 `- 우선순위`가 있었고 그 문서가 이 표시를 쓰고 있으면, 의존성이 풀린 다음 Task로 옮긴다. 어느 Task인지 분명하지 않으면 옮기지 않고 보고에 적는다.
4. **Phase 제목** — 그 Phase의 모든 Task가 완료면 제목 끝에 `✅`를 붙인다. 이미 있으면 건너뛴다.
5. **요약표** — Phase 요약표가 있으면 그 Phase의 완료 수와 상태(`대기` → `진행 중` → `완료 ✅`), 합계 줄을 고친다.
6. **진행 상황 줄** — `**📊 진행 상황**` 줄의 `(완료/전체 Tasks 완료, N%)`를 고친다. **숫자는 문서에서 직접 세어** 맞춘다(완료 표기된 Task 수 ÷ 본편 Task 수). 본편 합계에 넣지 않는다고 적힌 후속 로드맵 · 2차 로드맵 줄은 그 문서의 규칙대로 센다.
7. **최종 업데이트 줄** — `**📅 최종 업데이트**` 날짜를 오늘(`date +%F`)로 바꾸고, 괄호 안 요약이 있으면 이번에 바뀐 것 한 줄로 고친다.

그 밖의 규칙:

- **진행 중인 Task에 완료 표시를 붙이지 않는다.** 진행 상황을 남겨야 하면 기존 문구를 유지하고 짧은 메모만 덧붙인다.
- **원문을 지우지 않는다.** 계획과 달라진 것은 `**YYYY-MM-DD 메모**:`로 덧붙이고, 폐기된 항목은 ~~취소선~~으로 남긴다.
- **후속 로드맵의 Task**(접두 문자가 붙은 번호)는 그 파일 안에서 같은 방식으로 갱신하고, 본편 로드맵 요약표에 그 로드맵을 가리키는 줄이 있으면 완료 수 · 상태 · 날짜도 함께 맞춘다.
- **새 후속 작업**은 대화나 코드에서 명확히 드러난 경우에만 "마지막 완료 작업 다음"에 넣는다. 번호를 새로 매겨야 하면 3단계의 확인 대상이다.
- 마크다운 표를 손으로 정렬하지 않는다. 저장소에 포매터가 있으면 그것에 맡긴다.

### 규칙 문서 (`CLAUDE.md` · `AGENTS.md` · `shrimp-rules.md`) — 조건부

단순한 Task 완료는 갱신 사유가 아니다. 아래에 해당할 때만 고친다.

- 문서에 적힌 **현재 상태 서술**(구현 상태, 완료된 Phase, 테이블 · 정책 · 테스트 수 같은 수치)이 이번 작업으로 사실과 달라졌을 때
- 이번 작업에서 **새 금지 사항 · 함정**이 드러났을 때 → `[금지] + [근거] + [왜 발견이 늦는지]` 형식으로, 그 문서의 기존 절에 추가
- 검증 명령, lint · 테스트 기준선, 코드 표준이 바뀌었을 때
- 파일 · 컴포넌트 · 명령이 **생기거나 없어져서** 문서의 목록 · 경로 설명이 틀리게 됐을 때
- 여러 문서가 같은 내용을 중복으로 적고 있을 때 → **함께** 고쳐 어긋나지 않게 한다

수치를 고칠 때는 추정하지 않는다. 직접 셀 수 없는 값은 고치지 않고 보고의 "확인 필요"에 적는다.

### README.md — 조건부

- 현재 상태 · 기능 목록 절의 사실이 바뀌었으면(미구현 → 구현 완료 등) 그 줄을 현재형으로 고친다. 기존 문장 구조를 유지한다.
- 의존성 매니페스트(`package.json`, `pyproject.toml` 등)가 바뀌었으면 기술 스택 · 설치 절의 목록을 맞춘다.
- 실행 방법 · 환경변수가 바뀌었으면 해당 절과 예시 환경 파일의 **이름**을 맞춘다(값은 쓰지 않는다).

### PRD — 조건부

- 기능이 추가 · 변경돼 기능 ID나 화면 · 데이터 모델이 달라졌을 때만 고친다. 로드맵과 기능 ID 범위가 어긋나면 양쪽을 함께 맞춘다.
- "검증할 단 하나의 질문"에 답할 수 있게 됐으면 실측값과 함께 답을 적을지 3단계에서 확인한다.

### 그 밖의 문서 — 조건부

- `docs/guides/*`, 검증 기록, 운영 가이드는 이번 작업이 그 문서가 설명하는 대상을 바꿨을 때만 고친다.
- 끝난 계획 · 인수인계 문서는 내용을 고치지 않는다. 필요하면 맨 위에 "지난 기록" 안내만 덧붙인다.

해당 사항이 없는 문서는 건드리지 않는다.

## 3단계 — 적용 방식

문서 수정은 git으로 되돌리기 쉬우므로, 위 기준에 해당하면 **사용자 확인 없이 바로 Edit로 반영**한다. 다음 경우에만 수정하지 말고 먼저 묻는다.

- 1단계의 근거가 충돌하거나 완료 여부를 확신할 수 없을 때
- 로드맵에 없던 **새 Task를 만들어** 넣어야 할 것으로 보일 때
- PRD의 기능 정의 · 범위를 바꿔야 할 때
- 규칙 문서의 기존 규칙을 **삭제하거나 뒤집어야** 할 때
- 로드맵 파일이 없어 새로 만들어야 할 때

비밀 값(키, 토큰, 비밀번호)은 어떤 문서에도 쓰지 않는다. diff에 비밀 값처럼 보이는 것이 있으면 문서로 옮기지 않고 보고에 알린다.

## 4단계 — 완료 보고

```
## 문서 동기화 결과

**근거**: (인자 / git 변경 요약 / 태스크 도구 상태 중 사용한 것. 서로 달랐으면 그 차이)

- <로드맵 경로>: <수정함 — Task 004 완료 표시, 진행 상황 3/12 → 4/12 (33%)> | <수정 안 함 — 사유>
- <후속 로드맵 경로>: …
- CLAUDE.md: <수정함 — 내용 요약> | <수정 안 함 — 규칙 · 상태 변경 없음>
- (찾은 다른 규칙 문서): …
- README.md: <수정함 — 내용 요약> | <수정 안 함 — 상태 변경 없음>
- docs/PRD.md: <수정함 — 내용 요약> | <수정 안 함 — 기능 변경 없음>

**📊 진행 상황**: 완료 N / 전체 M Tasks (P%) — 현재 Phase: <이름>
**확인 필요**: (3단계에서 보류한 항목, 체크하지 못한 완료 기준, 직접 세지 못한 수치. 없으면 "없음")
**다음**: (커밋은 하지 않았습니다. 다음 우선순위 Task가 있으면 한 줄)
```

찾지 못한 문서는 줄을 만들지 않는다. 수정한 문서가 하나도 없으면 그 이유를 한 줄로 보고한다.
